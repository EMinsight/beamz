# CUDA multistep port and RTX3090 measurements

`backend="cuda_mstep"` now implements the two-step whole-column schedule from
[PR #308](https://github.com/beamzorg/beamz/pull/308) inside the existing CUDA
component. **The measurements below describe the initial port, before recovery
of Futhark's core optimizations.** The [matched-workload follow-up](cuda-mstep-futhark-followup.md)
supersedes its performance conclusion and records a large-domain CUDA multistep
win. Keep the schedule explicit while its selection envelope is measured.

All changes are local on `feat/cuda-mstep`. No push, PR modification or issue
publication was performed. The [OpenCL proposal](opencl-backend-proposal.md)
is a local issue draft.

## Implementation

The 16x32 core uses the existing rolling `PairStage` shared-memory layout to
compute H1, E1, H2 and E2 over a whole z column. Eligibility is selected per
8x16 quadrant. Source columns and their two-cell halos, CPML slabs and boundary
margins use edge queues. Intermediate storage consists of compact quadrant
slots for those edge dependencies and monitor sample dependencies, plus one
initialized spare quadrant. Pair outputs use a full alternate field bank.

The core calls the shared Yee curl, rounding, material and field-update
primitives. Edge work calls the established `UpdateComponent`; it advances CPML
at both substeps and reuses the existing symmetric-slab specialization where
valid. Source and DFT work call the existing CUDA operations at their original
phase and absolute timestep. Odd tails call the ordinary phase kernels.
Source batching, materials, DFT packing, graph caching, native chunking and
returned state remain shared with established CUDA.

A shared native validation repair also accepts inactive zero-thickness CPML
profiles/recurrence arrays. Their non-packed dimensions remain checked; active
profiles remain separable, and profile thickness must match recurrence storage.
Both CUDA schedules now run the one-wall cases that previously failed native
validation.

The component is version 0.22.0 / ABI 22 and needs rebuilding alongside this
Python checkout. The optional `beamz_cuda_mstep` target does not change `auto`'s
required streamed-target manifest. Explicit unsupported requests raise a
diagnostic. Initial scope and rebuild instructions are in [cuda/README.md](../../cuda/README.md).

## Correctness and device checks

Passed 93 selected host tests, 20 existing CUDA hardware regression cases and
all 29 new multistep hardware cases across the final parity and supplemental
runs. The latter compare complete fields, both CPML recurrence banks, DFT
accumulators, clocks and continuation with established CUDA and JAX. Cases cover
seeded states, scalar/packed/dense/lossy E materials, dense magnetic coefficients,
PEC, asymmetric CPML, all source phases, mode sources, windowed/interval DFTs,
BF16 recurrence, missing sources/monitors, odd/even steps, state donation and a
259-step run across native chunk boundaries. Recorder rejection is explicit.
Floating comparisons use a maximum absolute difference normalized by each
reference leaf's peak: 1e-5 against CUDA and 3e-5 against JAX. Integer state is
compared exactly.

Compute Sanitizer memcheck passed the two-step symmetric and odd asymmetric
CPML cases with **0 errors**. A short-column case with a real K=2 core and ring
wraparound passed racecheck with **0 hazards, errors or warnings**. The first
larger racecheck was stopped after more than nine minutes of instrumentation;
it is not counted as a completed check. The shorter case checks the same shared
stages and barriers, with fewer tiles and planes.

```console
python -m pytest tests/hardware/test_cuda_mstep.py
compute-sanitizer --tool memcheck --report-api-errors no --error-exitcode 99 \
  python -m pytest tests/hardware/test_cuda_mstep.py \
  -k 'complete_state and (binary-all-2 or lossy-right-3)'
compute-sanitizer --tool racecheck --report-api-errors no \
  --kernel-name kns=MstepColumnCore --racecheck-num-workers 4 --launch-count 1 \
  --error-exitcode 99 python -m pytest tests/hardware/test_cuda_mstep.py \
  -k short_column_sanitizer
```

API-error reporting is disabled because JAX 0.9.0's constant-symbol probing
generates recoverable `cuModuleGetGlobal_v2` CUDA_ERROR_NOT_FOUND reports.
Memory-access and synchronization instrumentation remains enabled. An initial
memcheck with API reporting confirmed those probes were the reported errors.

Local builds used CUDA 13.3.73, GCC 16.1.1, SM86 and precise arithmetic without
fast math. CUDA 12.4.1 compilation remains a CI gate; H100, other architectures
and multi-GPU hardware were not tested locally.

## Historical measurements: initial core

RTX3090 24 GB, driver 610.43.03, existing 370-W power limit, JAX 0.9.0. No power
or clock configuration was changed. Every case uses the same binary dielectric
waveguide, Gaussian source, two plane field DFT monitors with three frequencies,
float32 fields/recurrence and 128 steps. CPML is 12 cells thick. `all` has six
absorbing faces; `right` has one absorbing face and PEC on the other five.
The domain shape is physical `(z,y,x)`.

Each schedule/case runs in a fresh process. The second round reverses backend
order. Both rounds include first execution, three warmups and five timed samples.
The table uses the median of the ten warm samples. GCUPS counts physical domain
cells times full timesteps per second. Calls do not donate input state; source
conditioning is disabled. Sources, absorber updates, DFT processing and any
selected storage conversions are inside the executable timing. Setup and
compilation are excluded and reported separately.

|---|---|---:|---:|---:|---:|---:|
| all | 32×64×96 | 2.81 | 1.44 | 0.51× | 2.5% | 6.1 |
| all | 128×256×512 | 8.08 | 5.50 | 0.68× | 62.9% | 231.7 |
| all | 256×512×512 | 8.35 | 6.63 | 0.79× | 77.5% | 670.7 |
| all | 512×256×64 | 6.49 | 1.57 | 0.24× | 34.8% | 248.0 |
| right | 32×64×96 | 3.39 | 0.70 | 0.21× | 26.6% | 6.1 |
| right | 128×256×512 | 7.32 | 6.06 | 0.83× | 82.2% | 170.4 |
| right | 256×512×512 | 6.81 | 6.14 | 0.90× | 87.8% | 534.8 |

The established path retains its default scheduling/layout policy; the new
path uses canonical storage. The narrow established case selects its existing
storage permutation, with conversion costs included. These are comparisons
of the public policies, not isolated stencil kernels. Sanitizer host analysis
overlapped portions of the sweep; both timing rounds were stable and there was
no other sustained GPU workload. Repeat without instrumentation before using
these records to fit a selector or claim a small performance difference.

For the largest all-wall case, median setup is 5.81 / 5.80 seconds, executable
compilation 0.67 / 4.92 seconds and first execution 1.08 / 1.36 seconds for
CUDA / multistep. JAX reports peak live allocations of 10,444 / 10,920 MiB and
executable temporaries of 1,735 / 2,213 MiB. The compact intermediate alone is
671 MiB; plan buffers cost another 124 MiB. The latter are included in compiled
constants and add preparation/compilation cost.

For one-wall CPML, established CUDA uses its single-bank schedule, while
multistep also needs a full alternate bank. At the largest size, peak live
allocations are 8,187 / 10,263 MiB. Compact intermediate storage therefore does
not imply lower total memory use than established CUDA. JAX allocation counters
describe live buffers; they are distinct from allocator pools and total
`nvidia-smi` process/device memory.

[Raw records](cuda-mstep-rtx3090-2026-10-09.json) include all 28 process runs,
samples, setup/compile/first-execution times, memory, scheduler plans, device
telemetry, commit and source/binary fingerprints. Every final run uses the same
native extension and solver-source fingerprint.

```console
python scripts/benchmark_cuda_mstep.py \
  --shapes 32x64x96 128x256x512 256x512x512 512x256x64 \
  --steps 128 --samples 5 --rounds 2 --source gaussian --boundary all \
  --output-dir .cache/mstep-final-all
python scripts/benchmark_cuda_mstep.py \
  --shapes 32x64x96 128x256x512 256x512x512 \
  --steps 128 --samples 5 --rounds 2 --source gaussian --boundary right \
  --output-dir .cache/mstep-final-right
```

## Selection and unification

Keep established CUDA as the default. The initial core used the GPU less
effectively than established CUDA on this measured envelope. The narrow case
has few column tiles; the small cases publish most intermediates. These
geometric observations help explain the trend. The follow-up's CUPTI activity
profile isolates the core bottleneck and records the resulting optimizations.

Continue measuring compact addressing, halo recomputation, shared-stage
synchronization and material loads. Scalar H specialization is now implemented;
further candidates include fully eligible tiles and sharing edge geometry
across component updates.
Each change must retain the same full-state and sanitizer gates.

Before automatic selection, extend the measurements across CPML thickness and
faces, dense/lossy/magnetic materials, slab/mode source coverage, monitor density,
run length, donation and GPU model. Compare total cost including preparation,
native graph creation and memory headroom, not warm throughput alone. Require
a repeated win with a practical margin; retain an explicit override.

Once that envelope exists, unify the public names under one CUDA backend with
a schedule option. Keep the shared compiler, numerical primitives and native
source/DFT operations as the maintenance boundary. An OpenCL implementation
should reuse that contract and the compact planner, with its own device
measurements, rather than become a second solver with independent semantics.
