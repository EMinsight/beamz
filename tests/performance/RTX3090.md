# RTX 3090 CUDA versus origin/main protocol

`scripts/benchmark_rtx3090_cuda.py` compares the PR's `cuda_streamed` FDTD
backend with the exact `origin/main` revision on a single RTX 3090. The baseline
is the pre-PR BeamZ JAX/XLA implementation on the same GPU; it does not import or
register `beamz._cuda`. This distinguishes the custom CUDA kernels from a CPU
comparison, which would measure a different processor rather than the PR change.

The default profile is a homogeneous `96 × 128 × 192` float32 3D Yee grid with
PEC faces and 200 timesteps. It intentionally excludes sources, monitors, and
CPML: this is the FDTD update throughput that the streamed kernels replace. Each
side receives three allocator/clock warmups followed by eleven independent
already-compiled executable samples. The first lowering and executable compilation
are recorded separately and never folded into runtime throughput.

Run from the checked-out PR branch after building BeamZ's private optional CUDA
component as described in `cuda/README.md`:

```console
python scripts/benchmark_rtx3090_cuda.py
```

The command creates a temporary detached `origin/main` worktree, runs both sides
in fresh processes with the same JAX CUDA installation, then removes that
worktree. It writes these ignored artifacts to `benchmarks/results/rtx3090/`:

- `rtx3090-cuda-comparison.json`: raw samples, provenance, percentile statistics,
  deterministic bootstrap median intervals, and derived GCUPS.
- `rtx3090-cuda-comparison.md`: a compact table suitable for a PR comment.
- `rtx3090-cuda-comparison.png`: median runtime (with 95% bootstrap error bars),
  GCUPS, and compilation-time charts.

The process exits non-zero when custom CUDA is slower than the `origin/main`
baseline, making a regression visible in automated hardware jobs. Pass explicit
`--shape`, `--timesteps`, and `--samples` values to establish another controlled
record; do not compare differently shaped records.

## Verified RTX 3090 result

The default profile was measured on 2026-08-12 at candidate revision
`7a673042ed352f060145318a69051ad986fcccc5`, against baseline revision
`8490470713ccc42bcf52065785feeb0bbefc58ae` from `origin/main`:

| Implementation | Median runtime | 95% bootstrap CI | Throughput |
| --- | ---: | ---: | ---: |
| `origin/main` JAX/XLA | 71.018 ms | 69.993–71.814 ms | 6.644 GCUPS |
| PR `cuda_streamed` | 49.015 ms | 48.593–49.855 ms | 9.627 GCUPS |

The custom CUDA implementation was **1.449× faster** (95% independent-bootstrap
CI 1.419–1.470×), reducing median runtime by 31.0% and increasing update
throughput by 44.9%. Its separately measured compilation step was 21.0× faster.
Compared with the preceding verified CUDA result, specializing uniform full-PEC
updates reduced CUDA median runtime by another 2.6%. These figures are specific
to the hardware, revisions, and default profile above; rerun the command to
reproduce them or to measure another controlled profile.

The matching opt-in pytest gate is deliberately disabled on ordinary machines:

```console
BEAMZ_RUN_RTX3090_BENCHMARK=1 pytest tests/hardware/test_rtx3090_cuda_benchmark.py
```

## Follow-up experiments

Four proposed directions were evaluated on the same RTX 3090:

1. **Feature matrix — retained.** The matrix above prevents a fast uniform
   stencil from hiding regressions in heterogeneous materials, CPML, source
   injection, or DFT accumulation.
2. **CPML bulk kernel plus slab corrections — rejected.** Parity passed, but the
   twelve additional slab-kernel launches per timestep dominated the saved
   interior checks. Speedup versus main fell to 0.734× for heterogeneous CPML,
   0.764× with a source, and 0.772× with a source and monitor.
3. **Mixed-rank full-PEC material kernel — rejected.** Specializing scalar decay
   with dense source coefficients increased the heterogeneous-PEC CUDA median
   from 15.628 ms to 16.269 ms, about 4.1%. The generic broadcast-aware kernel
   remains faster on Ampere.
4. **Persistent source-free CPML graph — retained.** A dedicated typed FFI call
   now aliases fields and all twelve CPML recurrence buffers and captures the
   complete multi-step run in one CUDA graph. In a 21-sample same-binary A/B,
   the CUDA median fell from 25.416 ms to 24.726 ms: a 1.028× speedup with 95%
   bootstrap CI 1.020–1.043×. End-to-end speedup against main rose from 1.127×
   to 1.161× in that controlled A/B.
5. **Reusable graph executables — retained.** A bounded cache keyed by stream,
   pointers, shapes, attributes, and step count avoids recapturing and
   reinstantiating an identical graph. In a 21-sample same-binary A/B, median
   CPML runtime fell from 25.078 ms to 24.555 ms: 1.021× faster (95% CI
   1.009–1.037×). Cache hits are pointer-exact, and launches are protected from
   concurrent eviction until submission.
6. **Packed source inside the graph — retained.** The common single packed
   pre-E electric slab source is now updated before each H/E pair in the CUDA
   graph, with unsupported source schedules retaining the general JAX path.
   Median CPML+source runtime fell from 27.132 ms to 24.794 ms: 1.094× faster
   (95% CI 1.077–1.100×). The fused result was 1.289× faster than `origin/main`
   in that controlled run.
7. **Plane DFT inside the graph — retained.** A narrow fast path performs the
   weighted six-component gather, float32 complex accumulation, and sample
   weighting after every E update for a full-time rectangular plane monitor.
   Median CPML+source+monitor runtime fell from 31.649 ms to 25.247 ms: 1.254×
   faster (95% CI 1.248–1.263×), reaching 1.398× versus `origin/main`.
8. **Compile-time CPML descriptor specialization — rejected.** Hardware parity
   passed and the median moved from 25.247 ms to 25.021 ms, but the 1.009× ratio
   had a 95% CI of 0.997–1.018×. The sub-percent nominal gain did not justify
   hard-coding descriptor layout into the kernel.
9. **One packed CPML correction kernel per phase — rejected.** This reduced the
   earlier twelve slab launches to one correction launch per phase and passed
   parity, but the controlled 21-sample result remained inconclusive: 25.583 ms
   monolithic versus 25.290 ms split, or 1.012× with 95% CI 0.993–1.025×. The
   simpler single-pass recurrence remains enabled.
10. **Cooperative persistent multi-stepping — rejected.** A resident cooperative
   grid with device-wide H/E barriers passed complete hardware parity, but reduced
   the uniform-PEC speedup from 1.429× to 1.190×. The large generic kernel could
   not expose memory bandwidth as effectively as the high-occupancy phase kernels.
11. **Spatial three-component fusion — retained.** One spatial block now updates
   all H or E components so neighboring curl inputs are consumed together. In
   controlled A/B runs, CUDA medians improved 6.4% for uniform PEC, 3.0% for
   heterogeneous CPML, and 3.0% for rectilinear PEC; axis-uniform was neutral.
12. **Seven-box CPML interior/shell split — rejected.** Numerical parity passed
   after making the rounded boxes disjoint, but seven launches per phase raised
   heterogeneous-CPML runtime to about 29 ms and regressed below main (0.966×).
13. **Warp-shared monitor phase evaluation — retained.** Lane zero now computes
   each repeated Hann weight and frequency phase once and broadcasts it across 32
   point samples. The two-monitor median improved from 20.284 to 20.050 ms; the
   cadence-three case was neutral.

The remaining performance floor is the sponge-boundary case at 1.163×. Future
kernel work should start with Nsight Compute evidence for memory traffic,
register pressure, and warp divergence. True multi-timestep stencil blocking
will require either safe scratch-buffer ping-pong storage or a wavefront/diamond
schedule; the cooperative whole-grid shortcut does not retain enough occupancy
on Ampere.

## Fused full-step and temporal-blocking follow-up

At candidate revision `f0cb9ed`, the default 17-profile matrix was rerun against
the same `origin/main` revision `8490470`. The retained fast path uses an
XLA-owned ping-pong workspace and fuses a complete H→E Yee step: each block stages
the updated H values and their low halo in shared memory, consumes them directly
for E, and writes the six destination fields out of place. The Ampere-tuned
`32 × 16 × 2` core also supports dense material coefficients and axis-uniform
or fully rectilinear metrics. Sources, monitors, CPML, sponge, and mixed-face

The median speedup remains **1.339×**, while the newly fused profiles move
substantially: relative to the preceding CUDA matrix, uniform PEC runtime falls
17.5%, heterogeneous PEC 16.2%, axis-uniform PEC 19.4%, and rectilinear PEC
18.3%. Every profile is still a statistically supported win over main; the
slowest lower confidence bound is 1.146× for sponge boundaries.

Three numerically correct true two-step designs were also benchmarked and
rejected rather than retained as nominal optimizations:

1. A full volumetric shared-memory tile used about 83 KiB per block and ran at
   18.94 ms, roughly 45% slower than the pre-fusion path.
2. An asymmetric/directional tile reduced shared storage to about 46 KiB but
   still ran at 14.86 ms, about 45% slower than the tuned fused-step kernel.
3. An N.5D z-wavefront ring buffer reduced shared storage to about 28 KiB and
   reached 12.46 ms at its best z chunk, about 21% slower than fused-step.

On GA102, the extra halo work, synchronization, and live state required by a
second timestep cost more than the eliminated global traffic. The result is a
useful boundary: full-step fusion is profitable, but another timestep should not
be retained without a schedule that avoids redundant six-field halo updates.
The raw JSON, generated Markdown, and runtime/throughput PNG graph for this run
are under the ignored `benchmarks/results/rtx3090/fused-step-final/` directory.
